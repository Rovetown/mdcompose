# Publishing and keeping mdcompose maintained

Two things this document covers: what it takes to publish `mdcompose` so that `uv add mdcompose`, `pipx install mdcompose`, `pip install mdcompose`, and `poetry add mdcompose` all just work; and how to keep the published package maintained for security and Python-version currency with as little manual work as possible.

Nothing here is implemented yet beyond the supply-chain CI.
It is the plan.

## 1. Publishing to PyPI

`mdcompose` is a pure-Python package with a console-script entry point.
Once it is on PyPI, every installer above resolves it the same way; there is no separate step for `uv` or `poetry`.
They read the same index and the same wheel metadata.

### 1.1 What the package already has

`pyproject.toml` is close to complete:

- `name`, `version`, `description`, `readme`, `license` (SPDX `MIT`), `license-files`, `authors`, `keywords`, `classifiers`
- `requires-python = ">=3.11"` and pinned dependency floors
- `[project.urls]` with a homepage and an issues link
- `[project.scripts] mdcompose = "mdcompose.cli:run"`
- `hatchling` build backend, wheel packaging set to the `mdcompose` package

The `build` job in CI already builds the sdist and wheel and smoke-tests the installed console script, so a broken package cannot reach `main`.

### 1.2 What to add before the first release

- **Version bumping.** Done: `commitizen` owns `[project].version` and `cz bump`, dispatched from `.github/workflows/bump.yml`, derives the next version from the Conventional Commits and pushes the tag.
  No version-derivation layer (`hatch-vcs`, `setuptools-scm`) is used; see the decisions log in [TODO.md](../TODO.md) and [docs/versioning-explained.md](versioning-explained.md).
- **A [CHANGELOG.md](../CHANGELOG.md).** Done: Keep a Changelog format, regenerated by `cz bump`.
- **`Development Status` classifier** matching reality: currently `3 - Alpha`, move to `4 - Beta` or `5 - Production/Stable` when the version says so.
- **A project description that leads with what it is**, since PyPI shows the README.
  The current one does.
- **Confirm the name is free**: re-checked 2026-09-10, `mdcompose` returns 404 on `pypi.org/pypi/mdcompose/json`, `registry.npmjs.org/mdcompose`, and `github.com/Rovetown/mdcompose`.
  One dead 2020 shell tool shares the GitHub name; not a package, not a conflict.
  Register the repo before someone else does.

### 1.3 Trusted Publishing, not API tokens

The current standard is **Trusted Publishing**: PyPI trusts a specific GitHub Actions workflow in a specific repository through OIDC, and no long-lived API token is stored anywhere.

Setup:

1. On PyPI, before the first upload, add a **pending publisher** under the account's Publishing settings: project name `mdcompose`, owner `Rovetown`, repository `mdcompose`, workflow filename `release.yml`, environment `pypi`.
2. `release.yml` already does this: on a `v*` tag it builds the distributions and publishes to TestPyPI then PyPI with `pypa/gh-action-pypi-publish` and no password.
3. Create the GitHub Actions **environments** `testpypi` and `pypi` (the latter with a required reviewer) so a release cannot publish without a human approving the run. `release.yml` already gates its publish jobs on them.

Publish to **TestPyPI first** with the same mechanism (a separate pending publisher, `test.pypi.org`) and install from there once to check the wheel renders and the entry point runs.

### 1.4 Attestations and SBOM (PEP 740, PEP 770)

- **PEP 740** (digital attestations) is Final. `pypa/gh-action-pypi-publish` generates and uploads PEP 740 attestations by default when publishing through Trusted Publishing.
  Nothing extra to configure; it proves the wheel came from the workflow PyPI trusts.
- **PEP 770** (SBOMs in Python packages) is Accepted.
  It lets a wheel carry SBOM documents under `.dist-info/sboms/`.
  Tooling is still catching up; for now, generate the SBOM in CI (the `supply-chain` workflow does) and attach it to the GitHub Release.
  Revisit embedding once `hatchling` or a plugin supports it.

### 1.4a SBOM tool choice

Use **`cyclonedx-py`** (the `cyclonedx-bom` distribution), not `syft`, for the Python SBOM. `syft`'s generic Python cataloger reads only the `License` and `License-Expression` metadata fields and the [LICENSE](../LICENSE) file; it does not map a Trove license classifier (`License :: OSI Approved :: MIT License`) to a license entry.
Several common dependencies, `colorama`, `markdown-it-py`, `mdurl`, `prompt-toolkit`, declare their license only as a classifier, so a `syft` SBOM lists them with no license. `cyclonedx-py` maps PEP 639 fields and classifiers, and produces a complete-license SBOM.
The `supply-chain` workflow uses it and fails the build if any component still has no license.

A classifier like `License :: OSI Approved :: BSD License` is kept as the classifier string rather than an SPDX id, because "BSD License" does not say which BSD variant; that is correct behavior, and the license-allowlist script accepts the string.

### 1.5 The release checklist

1. Update [CHANGELOG.md](../CHANGELOG.md), move the classifier if the status changed.
2. `uv run pytest` on 3.11 and the default, `uv run ruff check .`, `uv run python scripts/check_licenses.py` after `uv sync --no-dev`.
3. Tag: `git tag v0.1.0 && git push --tags`.
4. The `release.yml` workflow builds, publishes to PyPI through Trusted Publishing after the `pypi` environment is approved, and creates a GitHub Release with the built artifacts and the SBOM attached.
5. `pipx install mdcompose` from a clean machine and run `mdcompose doctor`.

`pipx` and `uv tool install` are the recommended ways for an end user to get a CLI, because they isolate it in its own environment.
The README should say `pipx install mdcompose` or `uv tool install mdcompose` first, `pip install` second.

## 2. Automated maintenance

The goal is that a dependency advisory, a dependency release, or a new Python version produces a pull request on its own, and that nothing rots silently.

### 2.1 Dependency updates

Use **Renovate** (preferred) or Dependabot.

- Renovate understands `uv.lock` natively, groups related updates, can be set to auto-merge patch and minor updates once CI passes, and raises a single "Dependency Dashboard" issue listing everything pending.
  Add `renovate.json` with `"lockFileMaintenance": { "enabled": true }` so `uv lock --upgrade` runs on a schedule even when no `pyproject.toml` floor changed.
- Dependabot is zero-config to enable in the GitHub UI but weaker with `uv.lock` and does not group.
  If chosen, add `.github/dependabot.yml` with a `pip` ecosystem entry and a `github-actions` entry.

Either way, also enable **Dependabot security updates** in the repository's security settings: those raise a PR the moment an advisory affects a pinned version, independent of the update schedule.

### 2.2 Vulnerability scanning

Already in `supply-chain.yml`:

- `pip-audit --strict` against the exported runtime and full requirement sets, on every push and weekly. `pip-audit` reads the PyPA Advisory Database.
- `anchore/scan-action` (grype) against the CycloneDX SBOM at `severity-cutoff: medium`, as a second source (the GitHub Advisory Database).
  Locally, `grype` needs a vulnerability database no more than five days old and downloads it on first run; if that download is blocked, rely on `pip-audit`, which reaches the PyPA Advisory Database over plain HTTPS.
- `google/osv-scanner-action` against `uv.lock`, a third source (the OSV.dev aggregate).

Already in the repo, inert until it is on GitHub:

- **GitHub code scanning with CodeQL** (`codeql.yml`, `github/codeql-action`), the Python `security-and-quality` query suite, on push and weekly.
  Catches injection and unsafe-pattern classes the dependency scanners do not.
- **OpenSSF Scorecard** (`scorecard.yml`, `ossf/scorecard-action`), weekly, publishing to the Scorecard dashboard.
  It grades branch protection, pinned actions, token permissions, and the presence of exactly the files this document is about.

### 2.3 Pinning the workflows themselves

GitHub Actions are a supply-chain surface too.

- Pin every `uses:` to a full commit SHA, not a tag. `pinact` or Renovate's `helpers:pinGitHubActionDigests` preset does this and keeps them updated.
- Set `permissions:` to the minimum at the workflow level (`contents: read`), and raise it per job only where needed (`id-token: write` for the publish job, `contents: write` for the release job).

### 2.4 Python version currency

The CI matrix is `3.11` through `3.14` on three operating systems.
Keeping it current has two halves:

- **Adding a new Python.** When 3.15 reaches its first release candidate, add `"3.15"` to the matrix.
  Renovate does not do this for a raw matrix string; the hand edit is a two-minute job annually and is not worth a regex manager.
- **Dropping an end-of-life Python.** 3.11 reaches end of life in October 2027.
  The floor is a policy choice (see the decisions log in [TODO.md](../TODO.md)): raise `requires-python`, `[tool.ruff] target-version`, and the matrix in one commit around then. `python-eol.yml` already opens a maintenance issue monthly once the current floor is within 60 days of its `endoflife.date` entry.

### 2.5 What a fully wired repository looks like

- Branch protection on `main`: require the `test`, `lint`, `ascii`, `build`, and `supply chain / *` checks, require a review, disallow force-push.
- Renovate app installed, `renovate.json` with lock-file maintenance and grouped auto-merge for patch and minor.
- Dependabot security updates on.
- `supply-chain.yml` (present), `codeql.yml`, `scorecard.yml` added.
- `release.yml` publishing through Trusted Publishing behind a reviewed `pypi` environment.
- All `uses:` pinned to SHAs, kept current by Renovate.
- A yearly reminder issue for the Python floor, or a scheduled `endoflife.date` check.

The manual surface then is: review and merge dependency PRs (most auto-merge), approve the `pypi` environment on a release, and edit the matrix once a year.
